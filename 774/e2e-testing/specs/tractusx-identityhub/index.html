    Tractus-X IdentityHub (wallet and IssuerService): E2E test spec¶

    A partner whose wallet holds the right credentials gets the contract, and an offer meant for another company stays invisible to it.

    Repository: tractusx-identityhub · Spec 1.0 · Draft · Raw spec for your AI · All specs

    Note

    Not run end to end yet. The test proves the wallet by its effect: the connectors only agree when the partner's credentials are presented and accepted.

    1 · The product in brief¶

    Every company in the dataspace has a wallet that holds its verifiable credentials: proof that it is a member, which framework agreements it signed, and its BPN. The IssuerService hands these credentials out. When a partner asks for a catalog or a contract, its connector presents the credentials from its wallet, and the provider's connector checks them against the policy.

    2 · The journey the test tells¶

    Side Played by
    Your side (SUT) The provider's connector and wallet
    Partner side (engine) The partner's connector and wallet, where the tests run from
    1. The provider publishes an offer whose usage policy asks for membership and the DataExchangeGovernance framework agreement.
    2. The partner's connector presents the credentials from its wallet and negotiates.
    3. The provider's connector accepts them, and the contract is agreed.
    4. The provider publishes a second offer that only one other BPN may see.
    5. The partner asks the catalog and does not see the second offer.

    Variables (env.variables)

    id Kind What it is Example In the workflow
    product_internal_url variable/type/string, source: input, scope: sut Any data behind the asset. The test is about the credentials, not the data. http://tck-echo Filled from product_internal_url, a traefik/whoami echo service.
    access_policy config/connector/policy Who may see the first offer: active members. – Written in the manifest
    usage_policy config/connector/policy Active membership, the framework agreement DataExchangeGovernance:1.0 and the usage purpose cx.core.industrycore:1. Copy it from the template: these are the credentials the toolbox issues to both participants. – Written in the manifest
    other_company_policy config/connector/policy An access policy with one constraint: BusinessPartnerNumber isAnyOf a BPN that is neither the provider's nor the partner's. BPNL0000000000XX Written in the manifest
    other_company_bpnl variable/type/string, source: input, scope: engine A made-up BPN that belongs to no participant of the run. The other_company_policy uses it. BPNL0000000000XX Supplied when the TCK runs

    Runs in the workshop: Yes. Workflow input run-in-toolbox: true.

    4 · The tests¶

    Every row is one step. Every ☐ is one validate entry. The step names are TestLab's own: look each one up in the IDE's block catalog for its inputs.

    Test 1 · The partner's credentials are accepted and the contract is agreed¶

    tests/credentials_open_the_contract.yaml · id credentials-open-the-contract · Journey · Positive

    Proves: Wallet, credentials and the policy check work together. Without them no contract is agreed.

    setup

    # What happens Step Must be true
    1 Create the access policy. connector/provider/create_policy –
    2 Create the usage policy. connector/provider/create_policy –
    3 Create an asset with id tractusx-identityhub-e2e-asset. connector/provider/create_asset –
    4 Publish the offer under both policies. connector/provider/create_contract_definition –

    execution

    # What happens Step Must be true
    1 As the partner, find the offer, negotiate and start the transfer. connector/consumer/pull_data_filtered ☐ The asset id is the one created in setup.
    ☐ An agreement id is returned.
    ☐ An EDR token is returned.

    teardown

    # What happens Step Must be true
    1 Delete the contract definition. connector/provider/delete_contract_definition –
    2 Delete the asset. connector/provider/delete_asset –
    3 Delete the usage policy. connector/provider/delete_policy –
    4 Delete the access policy. connector/provider/delete_policy –

    Test 2 · An offer meant for another BPN is not in the partner's catalog¶

    tests/offer_for_another_company_is_hidden.yaml · id offer-for-another-company-is-hidden · Negative

    Proves: The provider reads the partner's identity from its credentials and hides what is not meant for it.

    setup

    # What happens Step Must be true
    1 Create the other_company_policy as access policy, and the usage policy. connector/provider/create_policy –
    2 Create an asset with id tractusx-identityhub-e2e-hidden-asset. connector/provider/create_asset –
    3 Publish the offer under other_company_policy and the usage policy. connector/provider/create_contract_definition –

    execution

    # What happens Step Must be true
    1 As the partner, ask the catalog for the hidden asset by its id. connector/consumer/query_catalog_with_filters ☐ The list of datasets is empty.

    teardown

    # What happens Step Must be true
    1 Delete the contract definition, the asset and both policies, in that order. connector/provider/delete_contract_definition –

    5 · Break it on purpose¶

    A check that cannot fail proves nothing. Make each change once, see the test go red for this reason, and change it back.

    Test Change Expect
    offer_for_another_company_is_hidden.yaml Put the partner's own BPN (engine_bpnl) into other_company_policy. The offer becomes visible, the list is not empty and the check fails.
    credentials_open_the_contract.yaml Expect a different asset id. The asset id check fails.

    6 · Watch out¶

    • A red result can also be the connector's fault. Say so in the pull request.
    • The negative test needs its own asset id, different from test 1, so that the two tests can run in any order.
    • Do not write a real BPN of a company into the test. Use the input variable.

    7 · Not in this spec¶

    • The wallet's own APIs (creating participants, storing credentials). The toolbox does that before the tests run.
    • Issuing a credential during the test.

    8 · Give it to your assistant¶

    Attach or paste the raw spec, then send:

    Build the E2E test project for Tractus-X IdentityHub (wallet and IssuerService) in tck/e2e, exactly as the spec
tractusx-identityhub.yaml describes it. The manifest id is tractusx-identityhub-e2e; every test
file repeats it as namespace. Write the required tests first: credentials_open_the_contract.yaml, offer_for_another_company_is_hidden.yaml.
Use only the steps the spec names, and look each one up in the block catalog
before you write its inputs. Every check in the spec becomes one validate entry.
Addresses, BPNs and secrets are variables, never values in a test.
Compile after each file and fix what the compiler reports.

    Done when¶

    The definition of done for every product, and:

    • tests/credentials_open_the_contract.yaml is green.
    • tests/offer_for_another_company_is_hidden.yaml is green.
